# Requirements Document

## Introduction

This feature provides runtime schema validation for DynamoDB tables, allowing developers to verify that the actual DynamoDB table schema matches the entity metadata defined through source generation. The validation is designed to be called during application startup (e.g., Lambda cold start) rather than on every operation, making it suitable for fail-fast validation in production environments.

The feature also introduces Local Secondary Index (LSI) support to the library, distinguishing between GSIs and LSIs in metadata for accurate schema validation and future CDK construct generation.

## Glossary

- **Schema Validation**: The process of comparing the actual DynamoDB table configuration (from DescribeTable API) against the expected configuration defined in entity metadata
- **GSI (Global Secondary Index)**: A DynamoDB index with a partition key and optional sort key that can be different from the base table's keys
- **LSI (Local Secondary Index)**: A DynamoDB index that shares the same partition key as the base table but has a different sort key
- **Projection**: The set of attributes that are copied from the base table into an index (ALL, KEYS_ONLY, or INCLUDE with specific attributes)
- **TTL (Time To Live)**: A DynamoDB feature that automatically deletes items after a specified timestamp
- **Entity Metadata**: The compile-time metadata generated by the source generator describing table structure, keys, indexes, and projections
- **Validation Result**: The outcome of schema validation containing errors (failures) and warnings (non-critical mismatches)

## Requirements

### Requirement 1

**User Story:** As a developer, I want to validate my DynamoDB table schema during application startup, so that I can detect configuration mismatches before processing requests.

#### Acceptance Criteria

1. WHEN a developer calls `TableName.ValidateSchemaAsync(dynamoDbClient)` THEN the system SHALL return a validation result containing any errors and warnings
2. WHEN the validation is called THEN the system SHALL use the DynamoDB DescribeTable API to retrieve the actual table configuration
3. WHEN the validation completes successfully with no errors THEN the system SHALL return a result indicating success
4. WHEN the validation finds critical mismatches THEN the system SHALL return a result with `IsValid = false` and a collection of error messages
5. WHEN the validation finds non-critical differences THEN the system SHALL return a result with warnings while still indicating success if no errors exist

### Requirement 2

**User Story:** As a developer, I want the schema validation to verify primary key configuration, so that I can ensure my entity's key attributes match the actual table.

#### Acceptance Criteria

1. WHEN the table's partition key attribute name does not match the entity metadata THEN the system SHALL report an error
2. WHEN the table's partition key attribute type does not match the expected type (S, N, B) THEN the system SHALL report an error
3. WHEN the table has a sort key but the entity metadata does not define one THEN the system SHALL report an error
4. WHEN the entity metadata defines a sort key but the table does not have one THEN the system SHALL report an error
5. WHEN the table's sort key attribute name does not match the entity metadata THEN the system SHALL report an error
6. WHEN the table's sort key attribute type does not match the expected type THEN the system SHALL report an error

### Requirement 3

**User Story:** As a developer, I want the schema validation to verify Global Secondary Index configuration, so that I can ensure my GSI definitions match the actual table.

#### Acceptance Criteria

1. WHEN the entity metadata defines a GSI that does not exist on the table THEN the system SHALL report an error
2. WHEN a GSI's partition key attribute name does not match the entity metadata THEN the system SHALL report an error
3. WHEN a GSI's partition key attribute type does not match the expected type THEN the system SHALL report an error
4. WHEN a GSI's sort key configuration does not match the entity metadata (missing, extra, or wrong attribute) THEN the system SHALL report an error
5. WHEN the table has GSIs that are not defined in the entity metadata THEN the system SHALL report a warning
6. WHEN a GSI's projection type is not ALL and no projection model is defined for that index THEN the system SHALL report a warning

### Requirement 4

**User Story:** As a developer, I want the library to support Local Secondary Index definitions, so that I can accurately model tables with LSIs and validate their schema.

#### Acceptance Criteria

1. WHEN a property is marked with `[LocalSecondaryIndex]` attribute THEN the source generator SHALL include LSI metadata in the entity metadata
2. WHEN the entity metadata defines an LSI that does not exist on the table THEN the system SHALL report an error
3. WHEN an LSI's sort key attribute name does not match the entity metadata THEN the system SHALL report an error
4. WHEN an LSI's sort key attribute type does not match the expected type THEN the system SHALL report an error
5. WHEN the table has LSIs that are not defined in the entity metadata THEN the system SHALL report a warning
6. WHEN an LSI's projection type is not ALL and no projection model is defined for that index THEN the system SHALL report a warning

### Requirement 5

**User Story:** As a developer, I want the schema validation to verify TTL configuration, so that I can ensure my TTL attribute matches the actual table.

#### Acceptance Criteria

1. WHEN the entity metadata defines a TTL attribute but the table does not have TTL enabled THEN the system SHALL report an error
2. WHEN the entity metadata defines a TTL attribute but the table's TTL attribute name is different THEN the system SHALL report an error
3. WHEN the table has TTL enabled but the entity metadata does not define a TTL attribute THEN the system SHALL report a warning

### Requirement 6

**User Story:** As a developer, I want the schema validation to verify index projection configuration, so that I can ensure my projection models are compatible with the actual index projections.

#### Acceptance Criteria

1. WHEN an index has projection type KEYS_ONLY or INCLUDE and no projection model is defined THEN the system SHALL report based on the configured strictness level
2. WHEN a projection model is defined for an index THEN the system SHALL validate that all projection model properties are available in the index projection
3. WHEN the validation strictness is set to Strict THEN missing projection models for non-ALL indexes SHALL be reported as errors
4. WHEN the validation strictness is set to Relaxed (default) THEN missing projection models for non-ALL indexes SHALL be reported as warnings

### Requirement 7

**User Story:** As a developer, I want the IndexMetadata to distinguish between GSIs and LSIs, so that the metadata accurately represents the index type for validation and tooling.

#### Acceptance Criteria

1. WHEN the source generator processes a `[GlobalSecondaryIndex]` attribute THEN the generated IndexMetadata SHALL have `IndexType = IndexType.GlobalSecondaryIndex`
2. WHEN the source generator processes a `[LocalSecondaryIndex]` attribute THEN the generated IndexMetadata SHALL have `IndexType = IndexType.LocalSecondaryIndex`
3. WHEN querying an index THEN the system SHALL use the index name regardless of whether it is a GSI or LSI

### Requirement 8

**User Story:** As a developer, I want clear and actionable validation error messages, so that I can quickly identify and fix schema mismatches.

#### Acceptance Criteria

1. WHEN a validation error is reported THEN the error message SHALL include the expected value from entity metadata
2. WHEN a validation error is reported THEN the error message SHALL include the actual value from the DynamoDB table
3. WHEN a validation error is reported THEN the error message SHALL identify the specific element (table, index name, attribute name) that has the mismatch
4. WHEN a validation warning is reported THEN the warning message SHALL explain why the difference may be acceptable
5. WHEN validation results are logged THEN the system SHALL use the existing IDynamoDbLogger interface for consistency

### Requirement 9

**User Story:** As a developer, I want the validation to be optional and non-blocking by default, so that I can choose when and how to enforce schema validation.

#### Acceptance Criteria

1. WHEN the validation method is not called THEN the system SHALL not perform any schema validation
2. WHEN the validation returns errors THEN the system SHALL not throw an exception by default
3. WHEN a developer wants to fail on validation errors THEN the system SHALL provide a `ThrowOnError()` method that throws `SchemaValidationException`
4. WHEN a developer wants to configure validation strictness THEN the system SHALL accept a `SchemaValidationOptions` parameter with strictness settings

### Requirement 10

**User Story:** As a developer, I want the IndexMetadata to include projection information, so that I can understand what attributes are available in each index.

#### Acceptance Criteria

1. WHEN the source generator processes an index with a projection model THEN the IndexMetadata SHALL include the projection type (ALL, KEYS_ONLY, INCLUDE)
2. WHEN the source generator processes an index with INCLUDE projection THEN the IndexMetadata SHALL include the list of projected attribute names
3. WHEN no projection model is defined for an index THEN the IndexMetadata SHALL default to projection type ALL
