# Requirements Document

## Introduction

Redesign the Global Secondary Index (GSI) and Local Secondary Index (LSI) attribute API for the Oproto.FluentDynamoDb 1.0 public release. The current `[GlobalSecondaryIndex]` attribute requires users to set `IsPartitionKey = true` or `IsSortKey = true` as named parameters, which is error-prone because forgetting these flags produces silent misconfiguration. The new design replaces this with three distinct, self-describing attributes — `[GsiPartitionKey]`, `[GsiSortKey]`, and `[LsiSortKey]` — so the key role and index type are encoded in the attribute name itself and cannot be omitted or confused. DynamoDB developers already know the GSI and LSI acronyms, so the naming is immediately recognizable. Three explicit attributes with no boolean flags means the key role is always clear from the attribute name alone. This is a clean breaking change with no backward compatibility requirement since there are no public users on 0.8.

## Glossary

- **Source_Generator**: The Roslyn incremental source generator (`Oproto.FluentDynamoDb.SourceGenerator`) that analyzes entity attributes at compile time and emits mapper code, table classes, index properties, schema validation, and keys-only projection records.
- **Entity_Analyzer**: The component within the Source_Generator (`EntityAnalyzer.cs`) that extracts property-level attribute metadata from entity class declarations.
- **Index_Aggregator**: The component within the Source_Generator (`IndexAggregator.cs`) that consolidates index definitions from multiple entities sharing the same table and detects configuration conflicts.
- **GSI**: A DynamoDB Global Secondary Index, which has its own partition key and optional sort key independent of the base table.
- **LSI**: A DynamoDB Local Secondary Index, which shares the base table's partition key but has a different sort key.
- **GsiPartitionKey_Attribute**: The new `[GsiPartitionKey]` C# attribute that marks a property as the partition key for a GSI.
- **GsiSortKey_Attribute**: The new `[GsiSortKey]` C# attribute that marks a property as the sort key for a GSI.
- **LsiSortKey_Attribute**: The new `[LsiSortKey]` C# attribute that marks a property as the sort key for an LSI.
- **Index_Model**: The internal source generator model (`GlobalSecondaryIndexModel`, `LocalSecondaryIndexModel`) representing parsed index metadata.
- **Aggregated_Index_Model**: The internal source generator model (`AggregatedIndexModel`) representing a consolidated index definition across multiple entities.
- **ProjectionType**: An enum (`All`, `KeysOnly`) controlling the DynamoDB projection configuration for an index.
- **Discriminator_Config**: Optional GSI-specific configuration for entity discrimination in multi-entity tables (DiscriminatorProperty, DiscriminatorValue, DiscriminatorPattern).
- **Table_Class**: The partial class generated by the Source_Generator that exposes typed index accessor properties (e.g., `table.StatusIndex`).
- **Keys_Only_Projection**: A read-only record auto-generated when an index has `ProjectionType = ProjectionType.KeysOnly`, containing only the index keys and base table keys.

## Requirements

### Requirement 1: GSI Partition Key Declaration

**User Story:** As a developer, I want to mark a property as a GSI partition key using a dedicated attribute, so that the key role is explicit and cannot be accidentally omitted.

#### Acceptance Criteria

1. WHEN a property is annotated with `[GsiPartitionKey("index-name")]`, THE Source_Generator SHALL recognize that property as the partition key for the named GSI.
2. THE GsiPartitionKey_Attribute SHALL accept the DynamoDB index name as a required positional constructor parameter.
3. THE GsiPartitionKey_Attribute SHALL expose an optional `Name` property for specifying the C# property name of the generated index accessor.
4. THE GsiPartitionKey_Attribute SHALL expose an optional `ProjectionType` property defaulting to `ProjectionType.All`.
5. THE GsiPartitionKey_Attribute SHALL expose optional `DiscriminatorProperty`, `DiscriminatorValue`, and `DiscriminatorPattern` properties for GSI-specific entity discrimination.
6. THE GsiPartitionKey_Attribute SHALL have `AttributeUsage` allowing multiple applications on the same property, so that a single property can serve as the partition key for multiple GSIs.

### Requirement 2: GSI Sort Key Declaration

**User Story:** As a developer, I want to mark a property as a GSI sort key using a dedicated attribute, so that the key role is explicit and cannot be accidentally omitted.

#### Acceptance Criteria

1. WHEN a property is annotated with `[GsiSortKey("index-name")]`, THE Source_Generator SHALL recognize that property as the sort key for the named GSI.
2. THE GsiSortKey_Attribute SHALL accept the DynamoDB index name as a required positional constructor parameter.
3. THE GsiSortKey_Attribute SHALL expose an optional `Name` property for specifying the C# property name of the generated index accessor.
4. THE GsiSortKey_Attribute SHALL expose an optional `ProjectionType` property defaulting to `ProjectionType.All`.
5. WHEN both a `[GsiPartitionKey]` and a `[GsiSortKey]` specify `Name` or `ProjectionType` for the same index, THE Source_Generator SHALL use the values from the `[GsiPartitionKey]` attribute as the authoritative source, with the `[GsiSortKey]` values serving as overrides only when the `[GsiPartitionKey]` does not specify them.
6. THE GsiSortKey_Attribute SHALL have `AttributeUsage` allowing multiple applications on the same property, so that a single property can serve as the sort key for multiple GSIs.

### Requirement 3: LSI Sort Key Declaration

**User Story:** As a developer, I want to mark a property as an LSI sort key using a dedicated `[LsiSortKey]` attribute, so that the index type and key role are both immediately clear from the attribute name alone.

#### Acceptance Criteria

1. WHEN a property is annotated with `[LsiSortKey("index-name")]`, THE Source_Generator SHALL recognize that property as the sort key for the named LSI.
2. THE LsiSortKey_Attribute SHALL accept the DynamoDB index name as a required positional constructor parameter.
3. THE LsiSortKey_Attribute SHALL expose an optional `Name` property for specifying the C# property name of the generated index accessor.
4. THE LsiSortKey_Attribute SHALL expose an optional `ProjectionType` property defaulting to `ProjectionType.All`.
5. THE Source_Generator SHALL treat any index declared via `[LsiSortKey]` as an LSI that inherits the base table's partition key.
6. THE LsiSortKey_Attribute SHALL have `AttributeUsage` allowing multiple applications on the same property, so that a single property can serve as the sort key for multiple LSIs.

### Requirement 4: Removal of Legacy Index Attributes

**User Story:** As a library maintainer, I want to remove the old `[GlobalSecondaryIndex]` and `[LocalSecondaryIndex]` attributes, so that there is a single unambiguous way to declare indexes.

#### Acceptance Criteria

1. THE Source_Generator SHALL not recognize the `GlobalSecondaryIndexAttribute` class after the redesign.
2. THE Source_Generator SHALL not recognize the `LocalSecondaryIndexAttribute` class after the redesign.
3. WHEN a developer references the removed attribute classes, THE compiler SHALL produce a standard compilation error indicating the types do not exist.

### Requirement 5: Source Generator Index Extraction

**User Story:** As a library maintainer, I want the source generator to extract index metadata from the new attributes, so that all downstream code generation continues to work.

#### Acceptance Criteria

1. WHEN the Entity_Analyzer encounters a `[GsiPartitionKey]` attribute on a property, THE Entity_Analyzer SHALL populate the Index_Model with the index name, partition key property reference, and all optional configuration values.
2. WHEN the Entity_Analyzer encounters a `[GsiSortKey]` attribute on a property, THE Entity_Analyzer SHALL populate the Index_Model with the index name, sort key property reference, and all optional configuration values as a GSI sort key.
3. WHEN the Entity_Analyzer encounters a `[LsiSortKey]` attribute on a property, THE Entity_Analyzer SHALL populate the Index_Model as an LSI with the sort key property reference and optional configuration values.
4. WHEN a GSI has both a `[GsiPartitionKey]` and a `[GsiSortKey]` referencing the same index name, THE Entity_Analyzer SHALL combine them into a single GSI definition with both partition key and sort key.
5. WHEN a GSI has only a `[GsiPartitionKey]` and no `[GsiSortKey]` for the same index name, THE Entity_Analyzer SHALL treat the GSI as having a partition key only with no sort key.

### Requirement 6: Multi-Index Property Support

**User Story:** As a developer, I want a single property to participate in multiple indexes with different roles, so that I can model overloaded GSI key patterns (e.g., a property is PK in one GSI and SK in another).

#### Acceptance Criteria

1. WHEN a property has both `[GsiPartitionKey("gsi1")]` and `[GsiSortKey("gsi2")]`, THE Source_Generator SHALL register the property as the partition key for `gsi1` and the sort key for `gsi2` independently.
2. WHEN a property has multiple `[GsiPartitionKey]` attributes with different index names, THE Source_Generator SHALL register the property as the partition key for each named GSI independently.
3. WHEN a property has multiple `[GsiSortKey]` attributes with different index names, THE Source_Generator SHALL register the property as the sort key for each named GSI independently.
4. WHEN a property has multiple `[LsiSortKey]` attributes with different index names, THE Source_Generator SHALL register the property as the sort key for each named LSI independently.
5. WHEN a property has both `[GsiSortKey("gsi1")]` and `[LsiSortKey("lsi1")]`, THE Source_Generator SHALL register the property as the GSI sort key for `gsi1` and the LSI sort key for `lsi1` independently.

### Requirement 7: Index Aggregation Compatibility

**User Story:** As a library maintainer, I want the index aggregation logic to work with the new attribute structure, so that multi-entity table index consolidation continues to function correctly.

#### Acceptance Criteria

1. WHEN multiple entities sharing the same table define the same index name with matching key configurations, THE Index_Aggregator SHALL consolidate them into a single index property on the generated Table_Class.
2. WHEN multiple entities sharing the same table define the same index name with different partition key DynamoDB attribute names, THE Index_Aggregator SHALL emit diagnostic FDDB053.
3. WHEN multiple entities sharing the same table define the same index name with different sort key DynamoDB attribute names, THE Index_Aggregator SHALL emit diagnostic FDDB054.
4. WHEN multiple entities sharing the same table define the same index name as both a GSI and an LSI, THE Index_Aggregator SHALL emit diagnostic FDDB055.

### Requirement 8: Diagnostic Validation for New Attributes

**User Story:** As a developer, I want clear compile-time diagnostics when I misconfigure the new index attributes, so that I can fix errors before runtime.

#### Acceptance Criteria

1. WHEN a GSI index name has a `[GsiSortKey]` but no `[GsiPartitionKey]` on any property within the same entity, THE Source_Generator SHALL emit a diagnostic error indicating the GSI is missing a partition key.
2. WHEN a GSI index name has more than one `[GsiPartitionKey]` on different properties within the same entity, THE Source_Generator SHALL emit a diagnostic error indicating duplicate partition keys for the same GSI.
3. WHEN a GSI index name has more than one `[GsiSortKey]` on different properties within the same entity, THE Source_Generator SHALL emit a diagnostic error indicating duplicate sort keys for the same GSI.
4. WHEN an LSI index name has more than one `[LsiSortKey]` on different properties within the same entity, THE Source_Generator SHALL emit a diagnostic error indicating duplicate sort keys for the same LSI.
5. WHEN a `[GsiPartitionKey]` is applied with an empty or whitespace index name, THE Source_Generator SHALL emit a diagnostic error.
6. WHEN a `[GsiSortKey]` is applied with an empty or whitespace index name, THE Source_Generator SHALL emit a diagnostic error.
7. WHEN a `[LsiSortKey]` is applied with an empty or whitespace index name, THE Source_Generator SHALL emit a diagnostic error.
8. WHEN the same index name is used with both `[GsiPartitionKey]` (or `[GsiSortKey]`) and `[LsiSortKey]` within the same entity, THE Source_Generator SHALL emit a diagnostic error indicating the index name is used as both a GSI and an LSI.

### Requirement 9: Table Creation Code Generation

**User Story:** As a developer, I want the table creation generator to produce correct DynamoDB `CreateTable` requests using the new attribute metadata, so that integration test table provisioning works.

#### Acceptance Criteria

1. WHEN a GSI is defined using `[GsiPartitionKey]` and optionally `[GsiSortKey]`, THE Source_Generator SHALL generate `CreateTable` code that includes the GSI with the correct key schema (partition key, and sort key if present).
2. WHEN an LSI is defined using `[LsiSortKey("index-name")]`, THE Source_Generator SHALL generate `CreateTable` code that includes the LSI with the base table's partition key and the annotated property as the sort key.
3. WHEN an index has `ProjectionType = ProjectionType.KeysOnly`, THE Source_Generator SHALL generate `CreateTable` code with `Projection.ProjectionType = ProjectionType.KEYS_ONLY` for that index.
4. WHEN an index has `ProjectionType = ProjectionType.All`, THE Source_Generator SHALL generate `CreateTable` code with `Projection.ProjectionType = ProjectionType.ALL` for that index.

### Requirement 10: Keys-Only Projection Record Generation

**User Story:** As a developer, I want keys-only projection records to be auto-generated for indexes configured with `ProjectionType.KeysOnly`, so that I can query indexes efficiently with type-safe projections.

#### Acceptance Criteria

1. WHEN a GSI is configured with `ProjectionType = ProjectionType.KeysOnly`, THE Source_Generator SHALL generate a read-only projection record containing the GSI partition key, GSI sort key (if present), and the base table keys.
2. WHEN an LSI is configured with `ProjectionType = ProjectionType.KeysOnly`, THE Source_Generator SHALL generate a read-only projection record containing the base table partition key, LSI sort key, and the base table sort key.
3. THE generated projection record SHALL follow the naming convention `{ResolvedIndexPropertyName}KeysProjection`.

### Requirement 11: Schema Validation Code Generation

**User Story:** As a developer, I want the schema validation generator to validate index configurations using the new attribute metadata, so that runtime schema mismatches are detected.

#### Acceptance Criteria

1. WHEN schema validation is generated for a GSI, THE Source_Generator SHALL validate that the DynamoDB table's GSI configuration matches the index name, partition key attribute, and sort key attribute (if present) declared via the new attributes.
2. WHEN schema validation is generated for an LSI, THE Source_Generator SHALL validate that the DynamoDB table's LSI configuration matches the index name and sort key attribute declared via the new attributes.

### Requirement 12: Entity Metadata Generation

**User Story:** As a developer, I want the mapper generator to include index metadata in the generated entity metadata, so that runtime index lookups and query routing work correctly.

#### Acceptance Criteria

1. WHEN generating entity metadata, THE Source_Generator SHALL include each GSI's index name, partition key DynamoDB attribute name, sort key DynamoDB attribute name (if present), and projection type.
2. WHEN generating entity metadata, THE Source_Generator SHALL include each LSI's index name, sort key DynamoDB attribute name, and projection type.

### Requirement 13: Documentation and Steering File Updates

**User Story:** As a developer consuming the library, I want the API reference and steering files to reflect the new index attribute API, so that I can learn the correct usage patterns.

#### Acceptance Criteria

1. WHEN the redesign is complete, THE steering file `fluentdynamodb.md` SHALL document the `[GsiPartitionKey]`, `[GsiSortKey]`, and `[LsiSortKey]` attributes with usage examples for GSI and LSI declarations.
2. WHEN the redesign is complete, THE steering file `entity-patterns.md` SHALL be updated to reflect the new index attribute patterns.
3. WHEN the redesign is complete, THE `CHANGELOG.md` SHALL include an entry describing the breaking change from `[GlobalSecondaryIndex]`/`[LocalSecondaryIndex]` to `[GsiPartitionKey]`/`[GsiSortKey]`/`[LsiSortKey]`.

### Requirement 14: Example Code Updates

**User Story:** As a developer learning the library, I want all example code to use the new index attributes, so that I am not confused by outdated patterns.

#### Acceptance Criteria

1. WHEN the redesign is complete, all example entity classes in the `Examples/` folder SHALL use `[GsiPartitionKey]`, `[GsiSortKey]`, and `[LsiSortKey]` instead of `[GlobalSecondaryIndex]` and `[LocalSecondaryIndex]`.
2. WHEN the redesign is complete, all unit test entity fixtures SHALL use the new index attributes.
