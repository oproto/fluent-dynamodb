# Requirements Document

## Introduction

This feature unifies three overlapping configuration mechanisms — key Prefix, Computed key format, and Discriminator pattern — into a single source of truth based on the normalized format string. The source generator auto-derives discriminator patterns from key formats at compile time and emits diagnostics when definitions conflict. This eliminates redundancy, prevents runtime mismatches, and reduces the number of code paths performing equivalent work.

This feature depends on the "Computed Field Format Normalization" feature (which normalizes Separator/Prefix/PrefixSeparator into a Format string in ComputedFieldMetadata). This feature extends that normalized format to also serve as the basis for automatic discriminator pattern derivation.

## Glossary

- **Source_Generator**: The Roslyn incremental source generator in `Oproto.FluentDynamoDb.SourceGenerator` that analyzes entity attributes at compile time and emits mapper, keys, metadata, and discriminator code
- **Format_String**: A .NET composite format string (e.g., `"ORDER#{0}"`, `"TENANT#{0}#USER#{1}"`) compatible with `string.Format()`, representing the full shape of a key value
- **Discriminator_Pattern**: A string with `*` wildcards (e.g., `"ORDER#*"`, `"TENANT#*#USER#*"`) used to identify which entity type a DynamoDB item belongs to by matching against its key value
- **Derived_Discriminator**: A Discriminator_Pattern automatically generated by replacing each `{N}` placeholder in a Format_String with `*`
- **Explicit_Discriminator**: A Discriminator_Pattern manually specified by the developer via DiscriminatorProperty/DiscriminatorPattern/DiscriminatorValue attributes, used when discrimination cannot be inferred from key format alone
- **ComputedFieldMetadata**: The runtime metadata class describing a computed field's source properties and format string (simplified by the format normalization feature)
- **EntityMetadata**: The compile-time and runtime model representing an entity's complete DynamoDB configuration including keys, indexes, and discriminators
- **MatchesEntity**: The generated static method on each entity that determines whether a DynamoDB item belongs to that entity type based on discriminator logic
- **PartitionKeyAttribute**: The user-facing attribute marking a property as the table's partition key, supporting optional Prefix and Separator properties
- **SortKeyAttribute**: The user-facing attribute marking a property as the table's sort key, supporting optional Prefix and Separator properties
- **GsiPartitionKeyAttribute**: The user-facing attribute marking a property as a GSI partition key, supporting optional DiscriminatorProperty/DiscriminatorPattern/DiscriminatorValue
- **DynamoDbTableAttribute**: The user-facing attribute marking a class as a DynamoDB entity, supporting optional DiscriminatorProperty/DiscriminatorPattern/DiscriminatorValue for table-level discrimination
- **ComputedAttribute**: The user-facing attribute declaring that a property's value is computed from other properties using a format or separator
- **Key_Format**: The normalized format string representing the full assembled shape of a key value, incorporating any prefix, separator, and computed field configuration

## Requirements

### Requirement 1: Format String Normalization for Non-Computed Keys

**User Story:** As a library maintainer, I want the source generator to normalize key prefix configurations on non-computed keys into a format string, so that all key shapes — computed and non-computed — have a unified format representation.

#### Acceptance Criteria

1. WHEN a PartitionKeyAttribute has a non-null, non-empty Prefix value and the property is not annotated with ComputedAttribute, THE Source_Generator SHALL derive a Key_Format of `"{Prefix}{Separator}{0}"` where `{Prefix}` is the PartitionKeyAttribute.Prefix value and `{Separator}` is the PartitionKeyAttribute.Separator value (defaulting to `"#"` when Separator is null)
2. WHEN a SortKeyAttribute has a non-null, non-empty Prefix value and the property is not annotated with ComputedAttribute, THE Source_Generator SHALL derive a Key_Format of `"{Prefix}{Separator}{0}"` where `{Prefix}` is the SortKeyAttribute.Prefix value and `{Separator}` is the SortKeyAttribute.Separator value (defaulting to `"#"` when Separator is null)
3. WHEN a PartitionKeyAttribute or SortKeyAttribute has a null or empty-string Prefix and the property is not annotated with ComputedAttribute, THE Source_Generator SHALL derive a Key_Format of `"{0}"`
4. WHEN a property has both a key attribute (PartitionKey or SortKey) with a non-null, non-empty Prefix and a ComputedAttribute, THE Source_Generator SHALL use the format string computed by the format normalization feature (which already incorporates the prefix) and SHALL NOT produce a separate non-computed Key_Format
5. WHEN a key attribute's Separator property is explicitly set to an empty string and the Prefix is non-null and non-empty, THE Source_Generator SHALL derive a Key_Format of `"{Prefix}{0}"` with no separator character between the prefix and the placeholder (e.g., PartitionKey with Prefix="ORDER" and Separator="" produces `"ORDER{0}"`)

### Requirement 2: Auto-Derive Discriminator Pattern from Key Format

**User Story:** As a library consumer, I want the source generator to automatically derive discriminator patterns from my key formats, so that I don't need to manually specify DiscriminatorPattern when the key shape already provides sufficient information for entity identification.

#### Acceptance Criteria

1. WHEN the Source_Generator has computed a Key_Format for a key property (partition key or sort key), THE Source_Generator SHALL derive a Discriminator_Pattern by replacing each `{N}` placeholder in the Key_Format with `*`
2. WHEN the derived Discriminator_Pattern for a Key_Format of `"ORDER#{0}"` is computed, THE Source_Generator SHALL produce the pattern `"ORDER#*"`
3. WHEN the derived Discriminator_Pattern for a Key_Format of `"TENANT#{0}#USER#{1}"` is computed, THE Source_Generator SHALL produce the pattern `"TENANT#*#USER#*"`
4. WHEN the derived Discriminator_Pattern for a Key_Format of `"TENANT#{0}#USER#{1}#"` is computed, THE Source_Generator SHALL produce the pattern `"TENANT#*#USER#*#"`
5. WHEN the Key_Format is `"{0}"` (no prefix, single placeholder), THE Source_Generator SHALL derive the pattern `"*"` and SHALL NOT use this pattern for MatchesEntity discrimination or emit it as a usable DiscriminatorProperty/DiscriminatorPattern pair in the EntityMetadata
6. WHEN an entity shares a table (same table name in DynamoDbTableAttribute) with at least one other entity and the entity's sort key has a derivable discriminator pattern that is not `"*"`, THE Source_Generator SHALL select the sort key's derived pattern for the MatchesEntity method without requiring the developer to specify DiscriminatorProperty or DiscriminatorPattern on the DynamoDbTableAttribute
7. IF an entity shares a table with at least one other entity and the entity's sort key format is `"{0}"` (or the entity has no sort key) and the entity's partition key has a derivable discriminator pattern that is not `"*"`, THEN THE Source_Generator SHALL fall back to the partition key's derived pattern for the MatchesEntity method
8. WHEN the Source_Generator auto-derives a discriminator, THE Source_Generator SHALL use the selected key property's DynamoDB attribute name (from `[DynamoDbAttribute]`) as the DiscriminatorProperty (e.g., `"sk"` for a sort key annotated with `[DynamoDbAttribute("sk")]`)
9. WHEN an entity has both a partition key and a sort key with non-trivial derived patterns (neither is `"*"`), THE Source_Generator SHALL use the sort key's derived pattern for discrimination and SHALL NOT combine or merge the two patterns
10. WHEN an entity is the only entity on its table (no other entity shares the same table name), THE Source_Generator SHALL still derive the Discriminator_Pattern from the key format but SHALL NOT require or enforce its use in MatchesEntity generation

### Requirement 3: Compile-Time Conflict Detection — Prefix vs Format

**User Story:** As a library consumer, I want the source generator to detect and report when my key prefix conflicts with an explicit computed format, so that I am alerted to contradictory definitions at compile time rather than runtime.

#### Acceptance Criteria

1. IF a property has both a key attribute (PartitionKey or SortKey) with a non-null, non-empty Prefix and a ComputedAttribute with a non-null Format that does not start with `"{Prefix}{Separator}"` using an ordinal (case-sensitive) comparison, THEN THE Source_Generator SHALL emit a compile-time diagnostic error with the code FDDB100, where Separator is the key attribute's Separator value defaulting to `"#"` when not explicitly set
2. THE FDDB100 diagnostic SHALL have severity Error and category "DynamoDb"
3. THE FDDB100 diagnostic message SHALL include the property name, the prefix value, the expected prefix-separator combination, and the conflicting format string
4. WHEN a PartitionKeyAttribute specifies `Prefix = "ORDER"` with Separator="#" and the ComputedAttribute specifies `Format = "TENANT#{0}"`, THE Source_Generator SHALL emit FDDB100 because `"TENANT#{0}"` does not start with `"ORDER#"`
5. WHEN a property has both a key attribute with a non-null, non-empty Prefix and a ComputedAttribute with a non-null Format that starts with `"{Prefix}{Separator}"` using ordinal comparison, THE Source_Generator SHALL NOT emit FDDB100
6. IF a property has a key attribute with a null or empty-string Prefix, THEN THE Source_Generator SHALL NOT emit FDDB100 regardless of the ComputedAttribute Format value
7. IF a property has a key attribute with a non-null, non-empty Prefix and a ComputedAttribute with a null Format (relying on separator-based concatenation), THEN THE Source_Generator SHALL NOT emit FDDB100

### Requirement 4: Compile-Time Conflict Detection — Discriminator vs Key Format

**User Story:** As a library consumer, I want the source generator to detect when my explicit discriminator pattern doesn't match my key format shape, so that I am alerted to inconsistencies that would cause incorrect entity filtering.

#### Acceptance Criteria

1. IF an entity specifies an explicit DiscriminatorPattern on DynamoDbTableAttribute and the entity has a key property whose derived discriminator pattern is neither `"*"` nor equal to the explicit pattern and the DynamoDbTableAttribute.DiscriminatorProperty value equals the key property's DynamoDbAttribute name (case-sensitive string comparison), THEN THE Source_Generator SHALL emit a compile-time diagnostic error with the code FDDB101
2. THE FDDB101 diagnostic SHALL have severity Error and category "DynamoDb"
3. THE FDDB101 diagnostic message SHALL identify the entity name, the DynamoDB attribute name being compared, the explicit discriminator pattern, and the derived discriminator pattern from the key format
4. WHEN an entity has `[DynamoDbTable("orders", DiscriminatorProperty = "sk", DiscriminatorPattern = "USER#*")]` and the sort key has `[DynamoDbAttribute("sk")]` with a derived format producing discriminator `"ORDER#*"`, THE Source_Generator SHALL emit FDDB101
5. IF an entity specifies an explicit DiscriminatorPattern on DynamoDbTableAttribute and the matching key property's derived discriminator pattern is `"*"` (no prefix, no discrimination capability), THEN THE Source_Generator SHALL NOT emit FDDB101 because the explicit pattern supplements rather than contradicts the key format

### Requirement 5: Compile-Time Warning — Overlapping Derived Patterns

**User Story:** As a library consumer, I want the source generator to warn me when two entities on the same table have overlapping auto-derived discriminator patterns, so that I can add more specificity to avoid ambiguous entity identification.

#### Acceptance Criteria

1. WHEN two entities share the same DynamoDB table and both have auto-derived discriminator patterns where one pattern's matched set is a strict superset of the other's (different specificity scores), THE Source_Generator SHALL emit one FDDB102 compile-time diagnostic warning per overlapping pair, identifying both entity names, their respective discriminator patterns, and the DynamoDB attribute being compared
2. THE FDDB102 diagnostic SHALL have severity Warning and category "DynamoDb"
3. WHEN the Source_Generator emits FDDB102 for an overlapping auto-derived pair, THE Source_Generator SHALL still resolve the overlap by generating exclusion guards in the less-specific entity's MatchesEntity method (the warning is advisory and does not prevent code generation)
4. WHEN Entity A has derived pattern `"ORDER#*"` and Entity B has derived pattern `"ORDER#*#LINE#*"` on the same table, THE Source_Generator SHALL emit FDDB102 because `"ORDER#*"` would also match items intended for Entity B
5. IF two entities have auto-derived discriminator patterns with the same specificity score (neither is a strict superset of the other, e.g., both derive `"ORDER#*"`), THEN THE Source_Generator SHALL NOT emit FDDB102 and SHALL instead rely on the existing same-score ambiguous overlap diagnostic
6. THE Source_Generator SHALL emit FDDB102 only when both overlapping patterns are auto-derived from key formats; IF one or both patterns are explicit (specified via DiscriminatorPattern on DynamoDbTableAttribute), THEN THE Source_Generator SHALL NOT emit FDDB102 for that pair
7. WHEN three or more entities on the same table have pairwise overlapping auto-derived patterns with different specificity scores, THE Source_Generator SHALL emit one FDDB102 diagnostic for each overlapping pair independently

### Requirement 6: Compile-Time Info — Redundant Explicit Discriminator

**User Story:** As a library consumer, I want the source generator to inform me when my explicit discriminator is redundant because it matches what would be auto-derived, so that I can simplify my entity definitions.

#### Acceptance Criteria

1. WHEN an entity specifies an explicit DiscriminatorPattern on DynamoDbTableAttribute and the DiscriminatorProperty value matches the DynamoDB attribute name of a key property (partition key or sort key) whose derived discriminator pattern is a case-sensitive exact string match to the explicit pattern, THE Source_Generator SHALL emit a compile-time diagnostic with the code FDDB103
2. THE FDDB103 diagnostic SHALL have severity Info, category "DynamoDb", and be enabled by default
3. THE FDDB103 diagnostic message SHALL include the entity name and the redundant pattern value, and state that the discriminator pattern is automatically derivable from the key format
4. WHEN an entity has sort key format `"ORDER#{0}"` producing derived pattern `"ORDER#*"` and also specifies `DiscriminatorProperty = "sk"` (matching the sort key's DynamoDbAttribute name) and `DiscriminatorPattern = "ORDER#*"`, THE Source_Generator SHALL emit FDDB103
5. WHEN an entity has both a partition key and a sort key with derived patterns and DiscriminatorProperty matches the partition key's DynamoDB attribute name, THE Source_Generator SHALL compare the explicit pattern against the partition key's derived pattern only
6. IF an entity specifies DiscriminatorValue (exact match) instead of DiscriminatorPattern, THEN THE Source_Generator SHALL NOT emit FDDB103 regardless of whether the value matches a derived pattern

### Requirement 7: Explicit Discriminator Preserved When Not Derivable

**User Story:** As a library consumer, I want to retain the ability to specify explicit discriminators for cases where entity identification cannot be inferred from key format alone, so that multi-entity tables with shared key shapes remain supported.

#### Acceptance Criteria

1. WHEN an entity specifies DiscriminatorProperty on DynamoDbTableAttribute pointing to a DynamoDB attribute name that does not match the DynamoDbAttribute name of any property annotated with PartitionKeyAttribute or SortKeyAttribute on the same entity, THE Source_Generator SHALL use the explicit discriminator configuration (DiscriminatorProperty, DiscriminatorValue, and/or DiscriminatorPattern) for MatchesEntity generation without attempting to auto-derive a discriminator from key formats
2. WHEN an entity specifies DiscriminatorProperty on GsiPartitionKeyAttribute pointing to a DynamoDB attribute name that does not match the DynamoDbAttribute name of the property carrying that GsiPartitionKeyAttribute, THE Source_Generator SHALL use the explicit GSI discriminator configuration for GSI query filtering without auto-derivation from the GSI key's format
3. WHEN an entity's key format for all key properties (partition key and sort key) produces only the pattern `"*"` (no discrimination capability) and the entity shares a DynamoDB table name (identical TableName in DynamoDbTableAttribute) with at least one other entity, THE Source_Generator SHALL NOT auto-derive a discriminator for that entity. IF the entity does not specify an explicit DiscriminatorProperty on DynamoDbTableAttribute, THEN THE Source_Generator SHALL generate a MatchesEntity method that returns true for all items passed to it
4. WHEN an entity has an explicit DiscriminatorValue (exact string match) set on DynamoDbTableAttribute, THE Source_Generator SHALL use it for MatchesEntity generation with equality comparison without auto-derivation, regardless of the entity's key format
5. WHEN an entity has an explicit DiscriminatorProperty on DynamoDbTableAttribute referencing a non-key attribute, THE Source_Generator SHALL still compute and store the Key_Format and DerivedDiscriminatorPattern in EntityMetadata for each key property as specified by Requirement 11, using them only for key building and mapping operations rather than for discrimination

### Requirement 8: MatchesEntity Generation Using Derived Patterns

**User Story:** As a library maintainer, I want the generated MatchesEntity method to use the derived discriminator pattern when available, so that entity filtering is consistent with key format definitions and requires no manual synchronization.

#### Acceptance Criteria

1. WHEN an entity has an auto-derived discriminator pattern that is not `"*"`, THE Source_Generator SHALL generate a MatchesEntity method that retrieves the discriminator property value from the item dictionary and returns `false` if the discriminator property is absent or its string value is null
2. WHEN the auto-derived pattern uses a StartsWith strategy (e.g., `"ORDER#*"`), THE Source_Generator SHALL generate a MatchesEntity check that verifies the discriminator property value starts with the literal prefix (e.g., `"ORDER#"`)
3. WHEN the auto-derived pattern uses a Complex strategy with multiple wildcards (e.g., `"TENANT#*#USER#*"`), THE Source_Generator SHALL generate a MatchesEntity check that verifies the discriminator property value starts with the first literal segment (e.g., `"TENANT#"`) AND contains each subsequent literal segment (e.g., `"#USER#"`)
4. WHEN an entity has both an auto-derived discriminator and one or more exclusion guards from overlapping patterns (as determined by the existing tautological exclusion analysis), THE Source_Generator SHALL generate the MatchesEntity method such that the positive match is evaluated first (returning `false` on mismatch), followed by each exclusion guard evaluated in sequence (returning `false` if any exclusion matches), and returning `true` only if the positive match succeeds and no exclusion guard matches
5. WHEN an entity has an explicit discriminator that differs from what would be auto-derived (validated as non-conflicting by FDDB101), THE Source_Generator SHALL use the explicit discriminator for MatchesEntity generation

### Requirement 9: GSI Discriminator Auto-Derivation

**User Story:** As a library consumer, I want discriminator patterns for GSI queries to be auto-derived from key formats when the GSI key has a prefix or computed format, so that GSI-based queries filter correctly without manual discriminator specification.

#### Acceptance Criteria

1. WHEN a GsiPartitionKeyAttribute is on a property that also has a ComputedAttribute or a co-located PartitionKeyAttribute/SortKeyAttribute with a non-null Prefix, THE Source_Generator SHALL derive a Discriminator_Pattern from the property's Key_Format (using the same `{N}` → `*` replacement algorithm defined in Requirement 2) and SHALL store it as the GsiDiscriminator on the IndexModel for that GSI
2. WHEN a GsiSortKeyAttribute is on a property that also has a ComputedAttribute or a co-located PartitionKeyAttribute/SortKeyAttribute with a non-null Prefix, THE Source_Generator SHALL derive a Discriminator_Pattern from the property's Key_Format but SHALL NOT use it as the primary GsiDiscriminator for the index (the GsiPartitionKeyAttribute-derived pattern takes precedence for index-level discrimination)
3. WHEN a GsiPartitionKeyAttribute specifies an explicit DiscriminatorProperty whose value equals the DynamoDbAttribute name of the property bearing that GsiPartitionKeyAttribute, THE Source_Generator SHALL validate the explicit DiscriminatorPattern against the derived pattern and emit FDDB101 if the two patterns differ as strings
4. WHEN a GsiPartitionKeyAttribute specifies an explicit DiscriminatorProperty whose value does NOT equal the DynamoDbAttribute name of the property bearing that GsiPartitionKeyAttribute, THE Source_Generator SHALL use the explicit discriminator configuration without validation against the GSI key's derived pattern
5. WHEN a GSI partition key property's derived discriminator pattern is `"*"` (Key_Format is `"{0}"` with no prefix and no computed format), THE Source_Generator SHALL NOT populate a GsiDiscriminator on the IndexModel for that index and SHALL NOT add discriminator-based filtering to queries executed through that index
6. WHEN the Source_Generator populates a GsiDiscriminator on an IndexModel from an auto-derived pattern, THE Source_Generator SHALL set the GsiDiscriminator's DiscriminatorProperty to the DynamoDbAttribute name of the GSI partition key property and SHALL set the strategy to StartsWith when the pattern ends with `*` after a literal prefix

### Requirement 10: Backwards Compatibility

**User Story:** As a library consumer, I want my existing entity definitions with explicit DiscriminatorProperty/DiscriminatorPattern/DiscriminatorValue to continue working without changes, so that this enhancement does not break existing projects.

#### Acceptance Criteria

1. THE DynamoDbTableAttribute class SHALL continue to expose DiscriminatorProperty, DiscriminatorValue, and DiscriminatorPattern as public settable properties with type `string?` and default value `null`
2. THE GsiPartitionKeyAttribute class SHALL continue to expose DiscriminatorProperty, DiscriminatorValue, and DiscriminatorPattern as public settable properties with type `string?` and default value `null`
3. THE PartitionKeyAttribute class SHALL continue to expose Prefix as a public settable property with type `string?` and default value `null`, and Separator as a public settable property with type `string?` and default value `"#"`
4. THE SortKeyAttribute class SHALL continue to expose Prefix as a public settable property with type `string?` and default value `null`, and Separator as a public settable property with type `string?` and default value `"#"`
5. WHEN a library consumer upgrades to the new version and their entity has an explicit DiscriminatorProperty and DiscriminatorPattern or DiscriminatorValue configured on DynamoDbTableAttribute or GsiPartitionKeyAttribute, THE Source_Generator SHALL produce a MatchesEntity method with identical matching logic to the previous version for that entity
6. THE Source_Generator SHALL NOT introduce any new required attribute properties or constructor parameters on existing attributes, though new optional properties with non-breaking defaults are permitted
7. WHEN an entity already has explicit DiscriminatorProperty and DiscriminatorPattern that are identical to the auto-derived pattern, THE Source_Generator SHALL emit FDDB103 with severity Info (not Warning or Error) and SHALL NOT change the generated MatchesEntity behavior
8. WHEN a library consumer upgrades to the new version, THE Source_Generator SHALL NOT emit any new diagnostics with severity Error or Warning for entity definitions that compiled without errors or warnings in the previous version, except for FDDB102 (overlapping patterns warning) which identifies a pre-existing correctness issue
9. IF an entity previously had no explicit discriminator configuration and the auto-derivation feature now provides a derived discriminator pattern, THEN THE Source_Generator SHALL apply the derived pattern to the MatchesEntity method, which may result in stricter filtering than the previous always-true or key-presence-only behavior
10. THE DynamoDbTableAttribute class SHALL continue to accept both the `string tableName` constructor and the `Type tableType` constructor without changes to their signatures

### Requirement 11: Key Format Metadata Availability

**User Story:** As a library maintainer, I want the derived key format and discriminator pattern to be available in the entity's compile-time metadata model, so that other generator components (mapper, keys builder, query discriminator) can use a single normalized representation.

#### Acceptance Criteria

1. THE Source_Generator's internal PropertyModel class SHALL include a NormalizedKeyFormat property of type `string?` for each key property (partition key, sort key), populated with the normalized format string (e.g., `"ORDER#{0}"`, `"TENANT#{0}#USER#{1}"`, or `"{0}"` for keys with no prefix and no computed format)
2. THE Source_Generator's internal PropertyModel class SHALL include a DerivedDiscriminatorPattern property of type `string?` for each key property, set to the derived Discriminator_Pattern (e.g., `"ORDER#*"`) when the NormalizedKeyFormat is not `"{0}"`, and set to null when the NormalizedKeyFormat is `"{0}"`
3. WHEN MapperGenerator, KeysGenerator, TableGenerator, or PatternOverlapAnalyzer need the normalized key format or derived discriminator pattern, each component SHALL read from the PropertyModel's NormalizedKeyFormat and DerivedDiscriminatorPattern properties rather than independently re-deriving from KeyFormat.Prefix, KeyFormat.Separator, and ComputedKey attributes
4. THE EntityAnalyzer SHALL compute and populate NormalizedKeyFormat and DerivedDiscriminatorPattern on each key PropertyModel during entity analysis, before the EntityModel is passed to any code generation component or overlap analysis
