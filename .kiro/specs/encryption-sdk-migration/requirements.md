# Requirements Document

## Introduction

This specification covers Phase 1 of the KMS encryption module overhaul: migrating from the obsolete `AWS.EncryptionSDK` package to the replacement `AWS.Cryptography.EncryptionSDK` package. The current implementation is structurally complete but throws `NotImplementedException` because the AWS SDK integration was never finished due to API confusion with the old package.

This phase focuses on completing the core encryption functionality with the new package while maintaining backward compatibility with existing interfaces. Future phases will add per-field key support and batch/transaction multi-key capabilities.

## Glossary

- **AWS_Encryption_SDK**: The AWS Encryption SDK, a client-side encryption library that uses envelope encryption with data keys protected by KMS master keys
- **AWS.Cryptography.EncryptionSDK**: The new/current NuGet package name for AWS Encryption SDK for .NET (replaces obsolete `AWS.EncryptionSDK`)
- **KMS_Keyring**: An AWS Encryption SDK component that uses AWS KMS keys to generate, encrypt, and decrypt data keys
- **Data_Key**: A symmetric key generated by KMS used to encrypt actual data; the data key itself is encrypted by the KMS master key
- **Encryption_Context**: A set of key-value pairs that provide additional authenticated data (AAD) bound to the ciphertext
- **CMM**: Cryptographic Materials Manager - manages the cryptographic materials (data keys) used for encryption/decryption
- **Caching_CMM**: A CMM that caches data keys to reduce KMS API calls
- **Field_Encryptor**: The `IFieldEncryptor` interface implementation that performs field-level encryption/decryption
- **Key_Resolver**: The `IKmsKeyResolver` interface that maps context identifiers to KMS key ARNs
- **AOT**: Ahead-of-Time compilation for .NET Native AOT deployment scenarios
- **IDataKeyCache**: A pluggable interface for caching data keys, allowing users to implement custom caching strategies (Redis, DynamoDB, in-memory, etc.)
- **CachedDataKey**: A record containing the plaintext data key, encrypted data key, and expiration timestamp for cache storage

## Requirements

### Requirement 1: Package Migration

**User Story:** As a library maintainer, I want to migrate from the obsolete AWS.EncryptionSDK package to AWS.Cryptography.EncryptionSDK, so that the encryption module uses supported AWS libraries.

#### Acceptance Criteria

1. WHEN the Oproto.FluentDynamoDb.Encryption.Kms project is built THEN the System SHALL reference AWS.Cryptography.EncryptionSDK package instead of AWS.EncryptionSDK
2. WHEN the package migration is complete THEN the System SHALL resolve all namespace and API changes required by the new package
3. WHEN the new package is referenced THEN the System SHALL maintain compatibility with AWSSDK.DynamoDBv2 version 4.x and AWSSDK.KeyManagementService version 4.x

### Requirement 2: Encryption Implementation

**User Story:** As a developer using the library, I want field encryption to actually work, so that sensitive data is encrypted before being stored in DynamoDB.

#### Acceptance Criteria

1. WHEN EncryptAsync is called with plaintext data THEN the System SHALL return ciphertext encrypted using AWS Encryption SDK with a KMS keyring
2. WHEN encrypting data THEN the System SHALL use the KMS key ARN resolved by the configured IKmsKeyResolver
3. WHEN encrypting data THEN the System SHALL include the field name and context ID in the encryption context for audit trails
4. WHEN encryption fails due to KMS access issues THEN the System SHALL throw a FieldEncryptionException with the field name, context ID, and key ARN
5. WHEN encrypting data THEN the System SHALL use an algorithm suite with key commitment to prevent key substitution attacks

### Requirement 3: Decryption Implementation

**User Story:** As a developer using the library, I want field decryption to work transparently, so that encrypted data is automatically decrypted when read from DynamoDB.

#### Acceptance Criteria

1. WHEN DecryptAsync is called with ciphertext THEN the System SHALL return the original plaintext using AWS Encryption SDK with a KMS keyring
2. WHEN decrypting data THEN the System SHALL validate that the encryption context in the ciphertext matches the expected field name and context ID
3. WHEN decryption fails due to context mismatch THEN the System SHALL throw a FieldEncryptionException indicating the validation failure
4. WHEN decryption fails due to KMS access issues THEN the System SHALL throw a FieldEncryptionException with appropriate details
5. WHEN decrypting data encrypted with a different KMS key THEN the System SHALL fail with a clear error message

### Requirement 4: Data Key Caching

**User Story:** As a developer, I want data key caching to reduce KMS API calls, so that encryption operations are cost-effective and performant.

#### Acceptance Criteria

1. WHEN EnableCaching is true in AwsEncryptionSdkOptions THEN the System SHALL use a caching cryptographic materials manager
2. WHEN caching is enabled THEN the System SHALL respect the DefaultCacheTtlSeconds configuration for cache entry expiration
3. WHEN caching is enabled THEN the System SHALL respect the MaxMessagesPerDataKey limit before rotating data keys
4. WHEN caching is enabled THEN the System SHALL respect the MaxBytesPerDataKey limit before rotating data keys
5. WHEN EnableCaching is false THEN the System SHALL generate a new data key for each encryption operation
6. WHEN different context IDs are used THEN the System SHALL maintain separate cache entries to ensure tenant isolation

### Requirement 5: AOT Compatibility

**User Story:** As a developer deploying to AOT environments, I want the encryption module to be AOT-compatible, so that I can use field encryption in Native AOT applications.

#### Acceptance Criteria

1. WHEN the encryption module is used in an AOT application THEN the System SHALL function without runtime code generation
2. WHEN the project is built with trimming enabled THEN the System SHALL not produce trim warnings for encryption code paths
3. WHEN the AWS.Cryptography.EncryptionSDK package has AOT limitations THEN the System SHALL document these limitations clearly
4. IF the new package is not AOT-compatible THEN the System SHALL provide guidance on workarounds or alternative approaches

### Requirement 6: Backward Compatibility

**User Story:** As an existing user of the library, I want the migration to not break my code, so that I can upgrade without changes to my application.

#### Acceptance Criteria

1. WHEN upgrading to the new package THEN the IFieldEncryptor interface SHALL remain unchanged
2. WHEN upgrading to the new package THEN the IKmsKeyResolver interface SHALL remain unchanged
3. WHEN upgrading to the new package THEN the AwsEncryptionSdkOptions class SHALL maintain all existing properties with the same defaults
4. WHEN upgrading to the new package THEN the FieldEncryptionContext class SHALL remain unchanged
5. WHEN upgrading to the new package THEN the FieldEncryptionException class SHALL remain unchanged

### Requirement 7: Error Handling

**User Story:** As a developer, I want clear error messages when encryption fails, so that I can diagnose and fix issues quickly.

#### Acceptance Criteria

1. WHEN the KMS key resolver returns null or empty THEN the System SHALL throw a FieldEncryptionException with message indicating key resolution failure
2. WHEN KMS returns an access denied error THEN the System SHALL wrap it in a FieldEncryptionException with the key ARN that was attempted
3. WHEN the encryption context validation fails during decryption THEN the System SHALL throw a FieldEncryptionException explaining the mismatch
4. WHEN an unexpected error occurs during encryption THEN the System SHALL wrap it in a FieldEncryptionException preserving the inner exception
5. WHEN an unexpected error occurs during decryption THEN the System SHALL wrap it in a FieldEncryptionException preserving the inner exception

### Requirement 8: Pluggable Data Key Cache (REMOVED)

**User Story:** As a developer, I want to provide my own data key caching implementation, so that I can use Redis, DynamoDB, or other caching solutions to reduce KMS API calls in distributed environments.

**Status: REMOVED** - This requirement has been removed from the current spec.

**Reason:** The AWS Encryption SDK for .NET handles data key generation internally and does not expose hooks for injecting cached data keys. Implementing this feature would require custom envelope encryption that breaks interoperability with other AWS Encryption SDK implementations (Java, Python, JavaScript).

**Recommended Alternative:** For applications requiring reduced KMS API calls, consider using the AWS KMS Hierarchical Keyring in a future specification. This AWS-provided solution stores branch keys in DynamoDB while maintaining full SDK interoperability.

**Cost Context:** KMS API calls cost approximately $0.03 per 10,000 requests. For most applications, this overhead is acceptable.

See design.md "Data Key Cache Deferral" section for detailed technical analysis.
